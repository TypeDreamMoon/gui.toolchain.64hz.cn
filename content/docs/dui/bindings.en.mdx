description: The three arrows that connect the tree to the class's code — a binding drives a property, a route calls a handler, a two-way binding mirrors a variable — member paths, when a binding updates, and Shown, which every widget has.

Three arrows connect the tree to the class's code:

| Written | Direction | Example |
| --- | --- | --- |
| `Prop <- Expr` | class to tree: the property follows the expression | `Text <- GetTitle()` |
| `Event -> Handler` | tree to class: the event calls a function of the class (also written `+=`, `=`) | `OnClicked -> HandleConfirm` |
| `Prop <-> Var` | both ways: the property and a variable mirror each other | `Value <-> Volume` |

"The class" is the user widget the tree compiles into — which is where UMG puts event handling too. Its functions and
variables may be written in C++ or in the Blueprint's graph. The right side of all three can go on through a **member
path** to an object the class holds (`Player.Name`, `Settings.Apply()`) — most often a [view model](/en/docs/dui/viewmodels).

## `<-` drives a property

```dui
class /Game/UI/WBP_Inventory

Widget Root {
    + VerticalBox { Spacing = 8 }
    Text Title { Text <- GetTitle() }
    Image Glow { RenderOpacity <- Fade() * 0.8 }
    Widget Badge { Shown <- Count() > 0 && !IsLocked() }
}
```

The right side is an expression, re-evaluated as the class runs. It may hold:

- a call to a function of the class, `Func()` or `Func(a, b)`;
- a variable of the class, `Volume` — including a `props` entry and a `viewmodels` entry;
- a member path through an object variable, `Player.Name`, `Player.Stats.Title`, or a call at its end,
  `Player.FormatGold(Player.Gold)`;
- a literal: a number, a string, `true`, `false`, or `@Resource`;
- operators, loosest first: `||`; `&&`; `==` `!=`; `<` `<=` `>` `>=`; `+` `-`; `*` `%`; and the prefixes `!` and `-`.
  Parentheses group.

There is no `/` — it belongs to paths and comments — and no `? :`, no indexing `Items[0]`, no array or dictionary
literals. Every operator added to the expressions has to be lowered into a Blueprint graph, taught to the VS Code
extension's scanner and documented in three places, so a division or a choice is a function on the class, and an index is
a function that takes one; for widgets, a choice is an [`if`](/en/docs/dui/control-flow).

A bare `Func()` binds that function directly; anything richer is compiled into a generated function. What the target
property needs:

- A setter ([DUI5005](/en/docs/diagnostics/dui5xxx#dui5005)) — a component's prop excepted, see
  [Writing a component](/en/docs/dui/components).
- To be a **whole** property of the widget, its visual or a behaviour
  ([DUI5008](/en/docs/diagnostics/dui5xxx#dui5008)): not a slot property, not a container's, not a field inside a struct
  (`AnchorData.SizeDelta <- …` is refused).

| Code | When |
| --- | --- |
| [DUI2011](/en/docs/diagnostics/dui2xxx#dui2011) | the right side does not parse |
| [DUI5004](/en/docs/diagnostics/dui5xxx#dui5004) | a function the class lacks, or a bare-bound one that takes parameters |
| [DUI5011](/en/docs/diagnostics/dui5xxx#dui5011) | an expression the compiler cannot lower into a function |
| [DUI5023](/en/docs/diagnostics/dui5xxx#dui5023) | a path segment its class does not have, or does not show to Blueprint |
| [DUI5024](/en/docs/diagnostics/dui5xxx#dui5024) | a path that goes on past a value that is not an object |

A path starts at a variable of the class (a `viewmodels` entry, a prop or a Blueprint variable), and every later segment
is a member, visible to Blueprint, of the class the segment before it holds. While an object along it is not set, the
binding is not evaluated and the property keeps the value it had.

In VS Code, with the editor running, completion after `<-` asks the editor what the class really declares, calls get
signature help, and hovering a function or variable shows its type; after `Player.` it offers the view model class's
members.

### When a binding updates

The compiler records every variable and member the expression reads. When **each** of them is FieldNotify — the
variable on this class, and every member along a path on an object that implements `INotifyFieldValueChanged` — the
binding is subscribed: it updates when one of them announces a change, and costs nothing in between. Otherwise it is
read every frame. A call with arguments (`Format(Gold)`) may read anything, so a binding holding one is always read
every frame; a view model offering the formatted value as a member is the way out.

`DreamUI.Binding.Dump` lists every live widget's bindings, how many update on a change and how many every frame, and
why. `DreamUI.Binding.ForcePoll 1` reads them all every frame, which tells a change nobody announced from a wrong
binding.

<Callout type="warn">
  A binding that reads only FieldNotify variables is no longer read every frame once its Blueprint is recompiled: it
  updates when they announce a change. C++ that assigns such a variable without broadcasting it — which FieldNotify never
  allowed — used to be covered up by the poll, and is not any more; `DreamUI.Binding.ForcePoll 1` finds it.
</Callout>

## `->`, `+=` and `=` route an event

```dui
class /Game/UI/WBP_Dialog

Widget Root {
    + HorizontalBox { Spacing = 16 }
    Native.Button Confirm { OnClicked -> HandleConfirm }
    Widget Cancel {
        + UIButton { OnClick -> HandleCancel }
    }
}
```

The left side is an event of the widget, its visual or a behaviour: a `BlueprintAssignable` multicast delegate (what the
`Controls/` family declares), an `FDreamUIEventDelegate` property (what the older `Interaction/` behaviours declare), or
a single-cast delegate. Every widget has `OnVisibilityChanged`, `OnFocusReceived` and `OnFocusLost`.

The operator says what happens to the event's other listeners:

| Operator | Means | Takes |
| --- | --- | --- |
| `+=` | Adds this listener beside the others. | A multicast delegate or an `FDreamUIEventDelegate`. |
| `=` | This is the event's one listener. | A single-cast delegate. |
| `->` | Either, by the event's kind. | Any event. |

`+=` on a single-cast delegate, which cannot hold a second listener, and `=` on a multicast event, which would have to
drop the listeners the control and the Blueprint graph added, are [DUI5025](/en/docs/diagnostics/dui5xxx#dui5025).

The right side is one of:

- a function of the class, no parentheses (`HandleConfirm`): it takes what the event sends;
- `emit` of an event the class declares, with its arguments (see [Writing a component](/en/docs/dui/components));
- a function of an object the class holds, by a member path (`Settings.Apply`). With parentheses, they are its
  arguments — expressions over the class, with the event's own parameters in scope by name (`Settings.SetVolume(Value)`);
  without them, it takes nothing or exactly what the event sends. Nothing is called while the object is not set.

```dui
class /Game/UI/WBP_Audio

viewmodels {
    SettingsVM Settings = new
}
events {
    Picked(Number Index)
}

VerticalBox Root {
    Native.Slider Volume { OnValueChanged += Settings.SetVolume(Value) }
    Native.Button Apply  { OnClicked += Settings.Apply() }
    Native.Button Pick   { OnClicked -> emit Picked(0) }
}
```

| Code | When |
| --- | --- |
| [DUI5010](/en/docs/diagnostics/dui5xxx#dui5010) | the left side is not an event of the destination |
| [DUI5025](/en/docs/diagnostics/dui5xxx#dui5025) | `+=` on a single-cast delegate, or `=` on a multicast event |
| [DUI6004](/en/docs/diagnostics/dui6xxx#dui6004) | a handler the class does not have |
| [DUI6005](/en/docs/diagnostics/dui6xxx#dui6005) | a handler whose parameters are not the event's |
| [DUI6018](/en/docs/diagnostics/dui6xxx#dui6018) | a function the object's class does not have, or does not let Blueprint call |
| [DUI6019](/en/docs/diagnostics/dui6xxx#dui6019) | arguments that do not fit the function |

The compiler resolves every route into `UDreamWidgetBlueprint::EventBindings`, and `UDreamUserWidget::BindEventBindings`
attaches them at Initialize. In the designer the same thing is the *Events* section of the details panel: its `+` creates
a custom event with the right signature and the route that names it.

<Callout type="warn">
  `FDreamUIEventDelegate`'s own per-instance event list is legacy and read-only. Bindings saved in it still fire and can
  still be removed from the panel, but new ones are not authored there: a binding of that kind calls a function on an
  arbitrary object with a literal argument, which UMG has no equivalent of and `.dui` has no syntax for. Opening a panel
  that holds one logs a warning naming it. Nothing is rewritten automatically — turning "call `Foo` on that behaviour with
  this value" into "call a handler on the user widget" would change what the game does — so re-author those as routes
  when you touch them.
</Callout>

## `<->` mirrors both ways

```dui
class /Game/UI/WBP_Audio

Widget Root {
    + VerticalBox { Spacing = 8 }
    Native.Slider Volume { Value <-> MasterVolume }
    Native.Toggle Mute { bIsOn <-> bMuted }
}
```

The property follows the variable, and a change the control makes is written back into it. The variable must be a
FieldNotify variable of the class, or a member of an object it holds:

```dui
Native.Slider Volume { Value <-> Settings.MasterVolume }
```

Writing a member back calls the object's `Set<Member>` when it has a BlueprintCallable one (one parameter), and otherwise
writes the member and announces it on that object. A member that cannot be written either way is
[DUI6020](/en/docs/diagnostics/dui6xxx#dui6020).

`<->` is two halves: forward, a generated getter, standing where any bound function stands; backward, a generated route
`OnValueChangedBP -> generated setter`. Every value control broadcasts its changes under that one conventional name, and a
destination without it is DUI5010. A name after `<->` that is not a variable of the class (as of the previous compile) is
DUI5011.

In VS Code, completion after `<->` lists the class's variables, FieldNotify ones first.

## `Shown`

Every widget has `Shown`: `true` is Visible, `false` is Collapsed. It keeps nothing of its own — reading it reads
`Visibility`, writing it writes `Visibility` — and it is what a condition binds:

```dui
class /Game/UI/WBP_Detail

Widget Root {
    + VerticalBox { }
    Widget Detail {
        Shown <- HasDetail()
    }
    Text Empty {
        Text = "Nothing selected"
        Shown = false
    }
}
```

A widget that is Hidden or hit-test invisible counts as shown, and keeps that state while `Shown` is `true`; it is not
made Visible. An `if` binds `Shown` on each widget of its branches; see [if and for](/en/docs/dui/control-flow). `Shown`
and `Visibility` are one value, and the designer's write-back compares only the face the file spells.

## Those are the language's; there is a run-time one too

The `<-` / `->` / `<->` above are all **language-level** bindings — resolved by the compiler, aware of FieldNotify and
view models.

There is also a **run-time** route: `UDreamDataBinding` — a **component** that connects **by property name through
reflection**, so it can join **any two `UObject`s** without knowing their types at compile time; the price is string
property names and reflection.

| Field | Default | Notes |
| --- | --- | --- |
| `SourceObject` / `SourceProperty` | empty | What to read from, and which property |
| `TargetObject` / `TargetProperty` | empty | What to write to, and which property — ⭐ **with `TargetObject` empty, it defaults to the widget that owns this component** |
| `UpdateMode` | **`OnAwake`** | `EDreamBindingUpdateMode`: `OnAwake` / `EveryFrame` / `Manual` |

The entry point is `ApplyBinding()` (callable from Blueprint).

### Changing the look by size: `UDreamResponsiveBehaviour`

`UDreamResponsiveBehaviour`, in the same file, is a **breakpoint** behaviour: by the **parent's size** (its own size on
the root) it applies **the first rule that matches**.

The fields of one `FDreamResponsiveRule`: `Name`, `MinWidth` / `MaxWidth` / `MinHeight` / `MaxHeight` (default **0**),
`Visibility`, `RenderOpacity` (default **1**).

⭐ **The line in the class comment is the thing to remember here**:

> A rule is an **override of the widget's authored look**, not a full description of it: **a size that matches no rule
> puts the widget back as it was**, rather than leaving it **in the last rule's costume**.

`ActiveRule` (`Transient`) records which rule is in effect; `bHasBaselineAppearance` with `BaselineVisibility` /
`BaselineRenderOpacity` holds the look **from before a rule first overrode it** — the record of "**what this component
borrowed**", and **deliberately not a `UPROPERTY`**: it means nothing across a load (`ActiveRule` is `Transient` too), so
**until it takes something again, it owes nothing**.

⚠️ Both types live in `Source/DreamGUI/Public/Interaction/DreamResponsiveBinding.h` — **that file holds
`UDreamDataBinding` too**; do not go looking for it elsewhere by its name.
